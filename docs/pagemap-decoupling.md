# 设计：让页码反查不再依赖 PDF 书签

> 状态：**方案设计（未实施）**
> 相关代码：`scripts/render_pw.js`（`outline: true`）→ `scripts/anime_pagemap.js`（`doc.getOutline()`）→ `evals/check.js` 的 `[C10]`/`[C11]`/`[C12]`/`[C17]`。
> 1.6.0 已修的：总览页标题不再生成同名书签（书名撞作品名导致页码取错页的那个 bug）+ `[C17]` 重复书签检测。**下面这件是根因层面的解耦，仍未做。**

## 一、现在的依赖链

```
build_anime_html.js ──► render_pw.js ──► anime_pagemap.js ──► _pagemap.json ──► 第二轮 build 印页码
   （目录页码占位）      （写书签）       （读书签反查页码）      （作品→页码）      ──► check [C11]/[C12]/[C17]
```

页码的**唯一来源是 Chromium 写进 PDF 的书签**（outline）。书签在，一切收敛；书签没了，`_pagemap.json` 变空，目录页码停在占位符。

## 二、为什么这是个脆点（实测证据）

| 操作 | 书签条数 |
|---|---|
| Chromium 单次渲染（`outline: true`） | 6 |
| 经 qpdf `--pages` 做页级合并后 | **0** |

也就是说 **qpdf 的页级操作会丢弃 outline**。于是这些需求全都不能做——做了就静默失灵：

- 封面/封底**单独渲染**（去掉封面页码、让品牌色带真正出血到纸边）
- 多册**合并**成一本合集
- 加一页**盖章页 / 版权页 / 勘误页**
- 换渲染器（换成 Prince / WeasyPrint / LaTeX 就没有书签这条路了）

另有一个已发生的实例：**书名与某部作品名相同时**，总览页标题也生成了同名书签，`anime_pagemap.js` 取最小页 → 目录页码印成总览页页码，而所有断言都"绿"（错得自洽）。1.6.0 用"总览页标题不用 `h1`" + `[C17]` 检测堵住了这一例，但**只要还有第二个来源能产生同名书签，同类问题就会再来一次**。

## 三、三个方案

### A. HTML 不可见锚点 + pdfjs 文本反查（推荐）

构建时在每章标题旁注入一个锚点，渲染后在 PDF **文本层**里找它在第几页。

```html
<h2 class="show-title">星海旅人<span class="pm" data-key="星海旅人">@@PM@@星海旅人</span></h2>
```
```css
.pm{ position:absolute; font-size:1px; color:transparent; white-space:nowrap; }
```

- **必须用 `color:transparent`，不能用 `display:none` / `visibility:hidden`**——后两者不会进 PDF 文字层
- 锚点前缀用 **ASCII**（如 `@@PM@@`）：中文字符若不在字体子集里会整个消失，ASCII 前缀永远在
- 比对沿用 `scripts/_titles.js` 的 `norm()`（去所有空白）

**好处**：与书签、渲染器、合并/分册全部解耦——锚点跟着页面走。**代价**：pagemap 从"读书签"变成"扫文本"，几十页的书可忽略不计。

### B. 构建期分页模型（不推荐）

用固定行高估算每章页数，构建期直接算页码。一轮构建即可、最快，但**估算必须与真实分页逐页一致**——册子里有海报、立绘、长简介折行，任何一处高度变化就是全书页码错位。风险远高于收益。

### C. 书签独立保存 + 合并后重注入（不推荐）

渲染时另存"标题→页码"，合并后用 pdf-lib 重写 `/Outlines`。改动最小，但 pdf-lib 并不支持写 outline（要手工构造对象），脆且复杂——**只是把依赖换个地方，没解决根因**。

## 四、推荐方案 A 的落地步骤

| 步 | 文件 | 改什么 |
|---|---|---|
| 1 | `scripts/build_anime_html.js` | 章节标题注入 `<span class="pm" data-key="…">@@PM@@…</span>` + 对应 CSS（不动版式） |
| 2 | `scripts/_pagemap.js`（新增） | `locateByAnchors(pdfPath, keys)`：用 pdfjs 扫文本返回 `{key: page}` |
| 3 | `scripts/anime_pagemap.js` | 改为 `--via=auto\|anchor\|outline`，**默认 auto**：先锚点；锚点一条都没命中时回退书签并打印 ⚠。迁移期两边都不炸 |
| 4 | `evals/pdfprobe.js` | 把锚点命中率写进 `_pdfprobe.json` |
| 5 | `evals/check.js` | 新增 `[C18]`（锚点命中每部）。按"编号只增不改"的规矩：**保留 `[C16]` 原义**（书签含每部），等书签彻底不再是页码来源后，再把它降级为"导航可用性"检查 |

## 五、先做一个 30 分钟 spike（在动主流程之前）

只有一件事没把握、但决定方案 A 成不成立：**透明 1px 文字是否稳定进入 Chromium PDF 的文字层，并被 pdfjs 提取到。**

```bash
# 一页 HTML：一个 .pm 锚点 + 一段正文 → Chromium 渲染 → pdfjs 提取文本，看 @@PM@@ 在不在
# 通过 → 按上面 5 步改；不通过 → 换招：把锚点做成白色实心 1px（非 transparent），仍不可见
```

## 六、回归测试（CI 的 fixture job 可直接加）

1. **删掉某章锚点** → 页码必须报缺失
2. **成品经 qpdf 合并后** → 页码仍应正确（这正是当前会失败的场景，改完后它必须过）
3. **Edge 兜底渲染** → 两轮页码一致（换渲染器不影响锚点方案）

## 七、迁移期的安全网

在方案 A 落地前，1.6.0 已加的这几条就是安全网，它们**报警但不解决问题**：

- `[C15]` PDF 正文含每部作品名（防字体子集吞字）
- `[C16]` PDF 书签含每部作品名（书签没了就报错，而不是让目录页码悄悄留占位符）
- `[C17]` 书签标题无重复（重名会让页码反查取错页）
